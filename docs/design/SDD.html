1. Introduction

This Software Design Document (SDD) describes the technical design for a Streamlit-based web application that allows vehicle owners and fleet managers to upload owner's manuals (PDFs, images, spreadsheets, and video) and query them using natural language questions.

Purpose & Scope

The application solves the problem: "How do I quickly find information in a 200-page owner's manual?" by providing an AI-powered search interface. Users upload documents once per session and ask questions like "What's the recommended tire pressure?" or "How do I reset the maintenance light?" The system retrieves relevant passages from all uploaded documents and generates natural language answers.

In Scope for v1.0: File upload (multi-format), natural language querying, session-based storage, error handling, response performance optimization.

Out of Scope for v1.0: User authentication, persistent storage, multi-user collaboration, analytics, mobile app (see SRS § 1.3 for details).

2. Architecture Overview

Deployment Shape

Single-Service Web Application. The entire application (UI, business logic, file parsing, querying, error handling) is deployed as a single Streamlit service. This is the simplest architecture that meets v1's requirements (few concurrent users, session-only storage, no external integrations).

Rationale: See ADR-0001: Use Streamlit as the Web Framework. Streamlit eliminates the need for a separate frontend/backend REST API, built-in session state management, and automatic web server setup. For v1's scale (few concurrent users) and scope (session-only, no authentication), this single-service model is simpler than microservices or frontend/backend separation.

External Dependencies

  • OpenAI API: For embeddings (text-embedding-3-small) and LLM inference (GPT-4 or GPT-3.5-Turbo). Required at runtime; requires valid API key.
  • No persistent database: v1 uses only in-memory storage (Streamlit session state) and temporary local caching. See ADR-0004.
  • No external services: File parsing, vector indexing (FAISS), and session management all run locally within the Streamlit process.

Key Constraints & Dependencies:
  • OpenAI API Key: Required to run the app. Users must provide a valid key. Cost is per-token (embeddings) + per-token (LLM inference). Monitor usage.
  • Python 3.9+: Streamlit requires Python 3.9 or later; some libraries (pandas, pdfplumber) may require 3.10+.
  • Memory: FAISS indexes are kept in-memory. For 10 documents with typical embeddings, ~50–100 MB memory per session. Scale v2+ if needed.
  • No persistent database for v1: All data is ephemeral (session-only). v2 migration will require database schema setup (see schema.sql).

5. API Boundary

The application is a Streamlit web app (not a traditional REST service). However, the data interfaces are well-defined via the OpenAPI specification, which documents:

  • File upload request/response schema
  • Query request/response schema
  • Session management endpoints
  • Error response formats

See: openapi.yaml for the complete API specification.

Key Endpoints (Implicit Streamlit Interface)

Endpoint (Logical) Method Purpose Request Schema Response Schema
/api/upload POST Upload and index a document file multipart/form-data { file, session_id } UploadResponse { status, filename, document_id, message }
/api/query POST Submit a natural language question application/json { query, session_id } QueryResponse { status, answer, sources[], confidence, response_time_ms }
/api/session/documents GET List all documents in the session N/A (session implicit) DocumentListResponse { document_count, documents[] }
/api/session/clear POST Clear session (delete all documents and state) N/A { message: "Session cleared successfully" }

Error Codes

Error Code HTTP Status Description
UNSUPPORTED_FORMAT 400 File format not in (PDF, image, Excel, PowerPoint, video)
FILE_TOO_LARGE 400 File size exceeds 50 MB
DUPLICATE_FILE 409 File already uploaded in this session (by hash)
PARSE_FAILED 400 Unable to extract text from file (corrupted, encrypted, etc.)
NO_DOCUMENTS 400 Query submitted but no documents in session
QUERY_TIMEOUT 408 Query processing exceeded 30 seconds
INTERNAL_ERROR 500 Unexpected server error

6. Data Boundary

v1.0 uses session-only in-memory storage. No persistent database. Data is automatically cleaned up when the session ends.

Session State Structure

All data lives in Streamlit's st.session_state dictionary:

st.session_state = {
    "session_id": "uuid-abc123",
    "created_at": 2026-08-19T10:30:00Z,
    "documents": {
        "doc_id_1": Document(
            document_id="doc_id_1",
            filename="Honda_Civic_Manual.pdf",
            file_format="pdf",
            uploaded_at=...,
            passages=[Passage(...), Passage(...), ...],
            parsed_successfully=True
        ),
        ...
    },
    "faiss_index": FAISS(...),  # In-memory vector index
    "passage_embeddings": {     # Map passage_id -> embedding vector
        "passage_0": [0.1, 0.2, ...],
        ...
    },
    "query_history": [
        Query(query_id="q_1", text="...", answer="...", sources=[...], ...),
        ...
    ]
}

Logical Data Model

For reference and future v2 migration, see the logical SQL schema in schema.sql. The schema documents:

  • sessions: User session metadata
  • documents: Uploaded file metadata
  • parsed_content: Text passages extracted from documents
  • embeddings: Vector embeddings of passages (reference; stored in-memory FAISS in v1)
  • queries: Query history
  • query_sources: Links queries to the passages used to answer them
Why no persistent database in v1? The SRS explicitly states documents are temporary (session-only); adding a database adds operational overhead (migrations, backups, access control) with no immediate value. v2 migration path is documented in schema.sql.

7. Internal Design

Component Responsibilities & Dependencies

Component Layer Single Responsibility Dependencies
UIPage Shell Render Streamlit pages and handle user interactions (file upload, query submission). Depends on: FileHandler, QueryProcessor, SessionManager
FileUploadHandler Shell Validate file (format, size), route to appropriate parser, manage file lifecycle. Depends on: DocumentParser, SessionManager, ErrorHandler
DocumentParser Core + Shell Extract text from files (PDF, image, Excel, PowerPoint, video). Core: parsing logic. Shell: API calls (OCR, video transcription). Depends on: PyPDF2, pdfplumber, EasyOCR, pandas, python-pptx, moviepy; OpenAI Whisper API (optional, for video)
EmbeddingGenerator Core + Shell Generate vector embeddings for passages and queries. Core: embedding logic. Shell: OpenAI API integration, caching. Depends on: LangChain, OpenAI API; caches via @st.cache_resource
SemanticIndexer Core Build and query FAISS in-memory index for semantic search. Depends on: FAISS, numpy
QueryProcessor Core Coordinate semantic search: embed query, search FAISS, retrieve top-K passages, score relevance. Depends on: EmbeddingGenerator, SemanticIndexer
AnswerGenerator Core + Shell Generate natural language answers using LLM. Core: prompt construction. Shell: OpenAI API calls, response parsing. Depends on: LangChain, OpenAI API
SessionManager Shell Manage session state lifecycle (create, store, clear on timeout/user action). Depends on: st.session_state
ErrorHandler Shell Catch exceptions, log them, and format user-friendly error messages (no stack traces, API keys, or internal details). Depends on: Python logging module

Dependency Graph & Loose Coupling

UIPage
├── FileUploadHandler
│   ├── DocumentParser (depends on format-specific libs)
│   ├── EmbeddingGenerator
│   ├── SemanticIndexer
│   └── SessionManager
├── QueryProcessor
│   ├── EmbeddingGenerator
│   ├── SemanticIndexer
│   └── AnswerGenerator
├── SessionManager
└── ErrorHandler (cross-cutting, all components depend on it)

Key Coupling Points:
- DocumentParser → EmbeddingGenerator: Flows parsed passages to embedding.
- QueryProcessor → AnswerGenerator: Flows retrieved passages to LLM.
- All components → ErrorHandler: For centralized error handling.
- All components → SessionManager: For session-state access.

Abstraction Boundaries:
- DocumentParser exposes Passage data class (no format-specific details leaked).
- QueryProcessor exposes QueryResult (answer + sources + confidence).
- EmbeddingGenerator exposes embedding vectors (Streamlit caches abstract away API).
- SemanticIndexer exposes search results (passage IDs + relevance scores).

Functional Core vs. Imperative Shell

DocumentParser

  • Core (Pure Logic): parse_pdf(), parse_image(), parse_excel(), parse_powerpoint() — extract text, no I/O side effects.
  • Shell (I/O): handle_upload() — routes to parsers, calls OCR APIs, handles errors.

EmbeddingGenerator

  • Core (Pure Logic): normalize_embeddings(), cache_key_for_passages() — utility functions.
  • Shell (I/O): embed_passages() — calls OpenAI API, caches results via @st.cache_resource.

SemanticIndexer

  • Core (Pure Logic): build_index(), search_by_similarity() — FAISS operations, no external I/O.
  • Shell (I/O): None; FAISS is fast enough that I/O optimization not needed for v1.

QueryProcessor

  • Core (Pure Logic): rank_passages_by_score(), filter_low_confidence() — scoring and ranking logic.
  • Shell (I/O): process_query() — orchestrates calls to EmbeddingGenerator and AnswerGenerator.

AnswerGenerator

  • Core (Pure Logic): build_prompt(), parse_llm_response() — pure text manipulation.
  • Shell (I/O): generate_answer() — calls OpenAI LLM API, handles timeouts/errors.

Design Principles Applied

Principle Application
Single Responsibility Each component has one reason to change (e.g., DocumentParser changes only if parsing logic changes; EmbeddingGenerator changes only if embedding strategy changes). Verified: one sentence per component responsibility (see table above).
Loose Coupling Components depend on data structures (Passage, QueryResult) and abstract interfaces (OpenAI API via LangChain) rather than internals. Files are not directly passed between components; they are parsed into Passages first.
High Cohesion All embedding-related logic (caching, OpenAI API calls) is in EmbeddingGenerator. All search-related logic is in QueryProcessor + SemanticIndexer.
Explicit Dependencies Components are initialized with their dependencies (e.g., AnswerGenerator receives EmbeddingGenerator, SessionManager). No hidden singletons or globals (except @st.cache_resource decorators, which are explicit).
Functional Core / Imperative Shell Business logic (ranking, scoring, prompt building) is pure and testable without mocking; I/O (API calls, file reading) is isolated in shell layers and mocked in tests.

8. Cross-Cutting Concerns

Error Handling

All errors are caught at component boundaries and routed through ErrorHandler, which:

  • Logs the full error (stack trace, context) for debugging.
  • Formats a user-friendly message (no stack traces, API keys, file paths).
  • Returns an ErrorResponse with an error_code (UNSUPPORTED_FORMAT, PARSE_FAILED, etc.) for client-side handling.

Example: If DocumentParser encounters a corrupted PDF, it raises ParseError. FileUploadHandler catches it, calls ErrorHandler.handle_exception(), and returns "Unable to parse this file..." to the user.

Observability & Logging

Python logging module (stdlib) with structured logs:

  • File uploads: Log filename, file_format, file_hash, parsed_successfully, parse time.
  • Queries: Log query_text, num_passages_retrieved, confidence, response_time_ms.
  • API calls: Log API (OpenAI), endpoint, request tokens, response tokens, latency.
  • Errors: Log exception, component, context (e.g., "error in file_upload during parsing").

Logs are written to stderr (default Streamlit behavior) and optionally to a file for later analysis.

Caching & Performance Optimization

Streamlit's rerun-on-interaction model can be expensive without caching. Mitigations:

  • @st.cache_data: Cache parsed passages (immutable data transformations). Cache key: file_hash.
  • @st.cache_resource: Cache FAISS index and OpenAI client. Cache key: session_id.
  • st.session_state: Store embeddings and query history per-session (not recomputed on rerun).

See ADR-0007 for caching strategy details.

API Key Management

OpenAI API key is required to run the app. Best practices:

  • Store in environment variable (OPENAI_API_KEY) or Streamlit secrets (.streamlit/secrets.toml).
  • Never log or display the key.
  • Rotate key if exposed; set rate limits in OpenAI dashboard.

12. Open Questions & Future Considerations

Explicitly Deferred (v2 Candidates)

  • User Authentication & Authorization: Add user_id tracking, login/logout, per-user document libraries. Requires database and session/token management. Deferred to v2.
  • Persistent Storage: Save documents and queries beyond session end. Requires database schema (see schema.sql) and migration of session-only data structures. Deferred to v2.
  • Vector Database Migration: Move FAISS from in-memory to a persistent vector DB (Pinecone, Weaviate). Required if documents need to persist across sessions. Deferred to v2.
  • Multi-User Collaboration: Share documents, collaborate on queries, annotations. Requires authentication + permissions. Deferred to v2+.
  • Advanced Analytics: Track which documents/queries are most popular, user satisfaction, model performance. Deferred to v2.
  • Fine-Tuned LLM: Train a model specifically on automotive manuals for higher accuracy. Current design uses general-purpose GPT-4; fine-tuning introduces data governance complexity. Deferred to v2+.
  • Mobile App: iOS/Android native app. v1 is web-only. Deferred to v2+ if mobile usage is high.
  • Batch Query Processing: Submit multiple questions at once. v1 handles one query at a time. Deferred to v2.
  • Custom NLP Models: Switch from OpenAI to a custom or open-source LLM (LLaMA, Mistral). Current design abstracts via LangChain; swapping is low-effort. Not deferred; just documented in ADR-0002 alternatives.

Open Design Questions (v1)

  • Session Timeout Duration: How long before inactive sessions are cleared? Recommend 1 hour based on typical manual-reading sessions, but should be configurable.
  • Max Documents per Session: Design supports 10 documents (to fit embeddings in memory); confirm this limit with stakeholders or implement dynamic limits based on available memory.
  • LLM Model Choice (GPT-4 vs. GPT-3.5-Turbo): GPT-4 is more accurate but slower/pricier. GPT-3.5-Turbo is faster/cheaper. Recommend starting with 3.5-Turbo and upgrading based on quality feedback.
  • Embedding Chunk Size: Passages are split into chunks for embedding. Optimal size? Recommend 512 tokens (~1,500 chars); adjust based on NFR-01 performance testing.
  • Relevance Threshold: What's the minimum relevance score to include a passage in the LLM prompt? Recommend 0.5 (cosine similarity) as a starting point; tune based on false positives/negatives in testing.
  • Cost Tracking: Should we track and report OpenAI API costs per session/user for billing? Not included in v1; can be added later if needed for paid tiers.

Known Limitations (v1)

  • No horizontal scaling: Single Streamlit service can't be load-balanced across multiple instances (session state is per-instance). Scaling v2+ requires a separate backend + frontend.
  • No caching of queries across sessions: If a user asks the same question twice (in different sessions), the query runs twice. v2 with persistent DB can cache query results.
  • Limited video support: Videos must have captions or OpenAI Whisper API enabled. No other audio/video analysis. Deferred to v2.
  • English-only (default): OCR and LLM work best for English. Multi-language support is not tested in v1.
  • No document versioning: If a user uploads a new version of the same manual (same filename, different content), it overwrites the old one in the same session. This is by design (session-only, no history), but can be improved in v2.
